## План по критичности и результаты

1. **P1, сохранность данных — исправлено:** первый показанный черновик теперь выбран для редактирования. Ранее при `current=null` текст отображался, но обработчик не сохранял правки. Instagram/TikTok-подписи сохраняются в выбранном черновике и восстанавливаются после перезагрузки. Типы коллекций из localStorage проверяются. Ошибка квоты/доступа больше не прерывает действие без объяснения: данные остаются в памяти, доступно скачивание копии.
2. **P1, API и сессии — исправлено на клиенте:** все обращения к Worker имеют ограничение времени; существующие 45/90 секунд сохранены, остальные — 120 секунд. Ответ 401 завершает текущую сессию; запоздалый 401 старой сессии не должен сбрасывать новую. Временный сбой проверки сессии больше не удаляет сохранённый токен. Автоматических повторов загрузки/публикации нет. После неоднозначной ошибки публикации показано предупреждение о проверке аккаунта перед повтором.

Нельзя решить синхронизацию переносом ключей в HTML или увеличением срока хранения токена. Нужны серверные сессии и общее хранилище черновиков с авторизацией, версиями и разрешением конфликтов.

Выполнять в кабинете, не присылать значения секретов:

3. Проверить хранение сессий в устойчивом серверном хранилище, независимость от isolate Worker, TTL, отзыв и ограничение попыток входа. Сейчас клиентский выход только очищает вкладку; серверный отзыв не виден в коде.
4. Проверить Gemini: binding секрета, доступную модель, квоты, обработку 429/5xx, ограничение размера/длины входа, отсутствие ключей и пользовательских токенов в логах. `/news/refresh` вызывается без сессии — проверить, нужны ли авторизация и ограничение расходов.

7. D1: реальные таблицы и миграции; владение строками, параметризованные запросы, ограничения и уникальность, резервные копии/восстановление. Для черновиков добавить версию записи и контроль конфликтов; сначала резервная копия локальных данных, затем обратимая миграция.

9. Очередь: определить, используется Cron/D1 или Cloudflare Queues; проверить trigger/binding, атомарный захват задания, lease, уникальный ключ операции, обработку повторной доставки, retry/backoff, failed/dead-letter, гонку cancel/publish, восстановление после рестарта и работу UTC/DST. ## Оставшиеся ограничения репозитория

- Несколько вкладок могут перезаписывать локальные данные; синхронизация/конфликты не реализованы. Резервная копия скачивается, интерфейса импорта пока нет.
- Клиент не хранит надёжный журнал промежуточных media/container ID для восстановления после потери сети. Идемпотентность нужно реализовать совместно с Worker, не добавляя произвольные поля неизвестному контракту.
- Часть API-путей принимает пустой JSON как отсутствие ошибки; для строгой проверки всех ответов нужен документированный серверный контракт. Генерация и авторизация уже проверяют обязательные поля.
- GitHub-токен менеджера источников находится в памяти вкладки; доступен исполняемому коду страницы. Следующий этап — серверная интеграция и CSP после выноса inline-кода. Секреты в клиент не добавлены.
- Кириллические тематические regex с `\b`/`\w` в fallback-хештегах могут выбирать менее точные общие теги; это не блокирует генерацию, результат проверяет редактор.
- Новостной сборщик загружает сайты из редактируемого списка. Требуется отдельное усиление разрешённых адресов/redirect/размеров при переносе его в окружение с внутренними сервисами.
- Общий пароль редакции не даёт персональных ролей и аудита действий. Настоящие пользователи/организации и серверный журнал — следующий этап.
